Glossary

Reference · System Design Fundamentals · authoritative terms — adhere to these in every lesson

Definitions are tuned for MAANG Staff interview use: precise, and phrased around client-visible effects. Backed by DDIA unless noted.

Consistency (CAP sense)
Linearizability. Every read sees the most recent completed write, as if there were one copy of the data and all operations were atomic on it. Strictly narrower than the everyday word "consistency". Not the "C" in ACID. See linearizability.
Availability (CAP sense)
Every request to a non-failing node returns a non-error response — eventually. Says nothing about latency. A 5-second response counts as available; an error does not.
Network partition
A link failure that splits nodes into groups that cannot talk to each other, while each group may still be reachable by clients. Not the same as a node crashing. Assumed unavoidable in any real distributed system.
CAP theorem
When a partition happens, a system must choose: keep serving reads/writes on both sides and risk stale/divergent data (AP), or refuse requests on at least one side to protect linearizability (CP). "Pick 2 of 3" is a misleading shorthand — P is not optional, so the real choice is C vs A during a partition. Source: Kleppmann 2015, Brewer 2012.
PACELC theorem
Extends CAP with the normal case. Partition → choose Availability or Consistency; Else (no partition) → choose Latency or Consistency. Captures that synchronous replication costs latency on every write, partition or not. Source: Abadi 2010.
Linearizability
A recency guarantee on a single object: once a write completes, every later read (by wall-clock time) returns that value or a newer one. The strongest single-object consistency model. Requires coordination → costs latency and availability.
Eventual consistency
If writes stop, all replicas converge to the same value eventually. Gives no bound on how long, and permits reading stale or out-of-order values in the meantime. The default "A/L" side of PACELC.
Scalability
Capacity grows by adding resources. Vertical = a bigger machine (simple, hard ceiling). Horizontal = more machines (needs statelessness or partitioning; the default at scale).
Availability (nines)
Fraction of time the system serves requests successfully. 99.9% ≈ 8.8 h/yr down; 99.99% ≈ 52 min/yr; 99.999% ≈ 5 min/yr. Each extra nine roughly 10x's the engineering cost — match to business impact.
Latency vs throughput
Latency = time for one request (quote p50/p99, never the mean). Throughput = requests completed per second. Independent: batching raises throughput and latency together.
Functional / non-functional requirement
FR = what the system does (a testable feature). NFR = how well it must do it, stated as a number (SLA/SLO). NFRs dictate architecture; FRs sit on top of it.
Modular monolith
One deployable unit, internally split by business domain; modules talk only through public APIs and never touch each other's tables. The recommended default before microservices.
Conway's Law
A system's structure ends up mirroring the communication structure of the org that built it. Corollary: choosing microservices is also choosing an org shape.
MoSCoW
Requirement prioritisation: Must / Should / Could / Won't-have. Forces explicit scope cuts instead of implicit ones.
