What system design is

Lesson 0002 · System Design Fundamentals · Section 1 · ~5 min

Mission tie-in: this is the frame the whole MAANG loop runs on. If you can't say in one sentence what the interviewer is grading, you'll spend 45 minutes drawing boxes and score a "no hire". This lesson fixes the frame.

1. The definition worth memorising

System design is choosing the building blocks a system is made of (clients, load balancers, services, caches, databases, queues, CDNs), deciding how they interact, and predicting how the whole thing behaves under real-world stress — load spikes, node failures, network partitions, bad deploys — then accepting the trade-offs that behaviour forces.1

Contrast with coding:

Coding asksSystem design asks
QuestionHow do I implement this correctly?How does it stay correct, fast and available under stress?
UnitFunctions, classes, algorithmsServices, APIs, data stores, infrastructure
Failure looks likeWrong outputCorrect output that arrives too late, or not at all, for some users

2. The four qualities everything trades against

Almost every design decision is bought with one of these and paid for with another:

  • Scalability — capacity grows by adding machines, not by praying.
  • Availability — keeps answering when components die.
  • Latency — answers fast, everywhere in the world.
  • Consistency — every reader sees correct, agreed-upon data.

You met the sharpest version of the last two in Lesson 0001: consistency is routinely traded for latency (PACELC's "else" branch) and for availability (during partitions).

3. What the interviewer is actually grading

The real rubric Not "did you name Kafka." It's: did you scope the problem, quantify the load, justify each component against the alternative, and name the failure modes and trade-offs before being asked. That last clause is the Senior→Staff line.

A candidate produces a clean architecture diagram in 10 minutes and stops. Most likely Staff-loop outcome?

A diagram is table stakes. The signal lives in estimation, per-component justification, and unprompted failure-mode / trade-off reasoning. Finishing early usually means the depth pass never happened.
Read this next (primary source): Kleppmann, Designing Data-Intensive Applications, Chapter 1 — "Reliable, Scalable, and Maintainable Applications". ~30 min. It defines the exact qualities above with precision you can quote in an interview.

Recall

Which best separates system design from coding?

The distinction is the failure model, not the tools or the seniority. Design work is about what happens at 10x load, on node loss, and during a partition — while still returning correct answers.
