CAP vs PACELC

Lesson 0001 · System Design Fundamentals · Section 2 · ~8 min

Mission tie-in: at a MAANG Staff loop, "we'll use Cassandra / DynamoDB / Spanner here" is only worth points if you can say what that buys and what it costs. CAP and PACELC are the vocabulary for that sentence. This lesson makes you use them precisely — not as slogans.

1. The one-sentence version

A distributed data store cannot make network partitions disappear, so its designers have already chosen — for you — how it behaves when one happens, and how much latency it spends on consistency the rest of the time. Your job in an interview is to name that choice out loud and defend it for the workload.

2. CAP, stated so it's actually true

The popular phrasing — "pick 2 of Consistency, Availability, Partition-tolerance" — is misleading and interviewers notice.1 Partitions are not a property you opt into; packet loss happens. So P is not on the menu. The real statement:

When a network partition occurs, you must choose between Consistency (linearizability) and Availability for the affected data. When there is no partition, CAP says nothing at all.

Precise definitions matter here — they're in the glossary:

  • Consistency = linearizability: a read never returns a value older than a write that already completed.
  • Availability = every request to a live node eventually gets a non-error answer. Latency is not part of it.

What the choice looks like during a partition

ChoiceBehaviour on the minority sideClient-visible effect
CP (choose consistency)Refuse writes (and often reads) it can't confirmErrors / timeouts until the partition heals. No wrong answers.
AP (choose availability)Keep accepting reads and writes locallyRequests succeed, but reads may be stale and concurrent writes may conflict and need later reconciliation.

During a partition, a CP store's minority-side node receives a write. What does a correct client see?

CP protects linearizability by declining what it cannot confirm. It returns an error — it does not serve stale data and does not fake a success. "No answer" is acceptable under CAP; "wrong answer" is not.

3. PACELC — the half CAP ignores

CAP only speaks about the partition case, which is rare. PACELC adds the common case:2

Partition? → trade Availability vs Consistency.   Else (normal operation) → trade Latency vs Consistency.

The "else" clause is the insight: keeping replicas linearizable means a write must reach a quorum (or the leader must wait for acks) on every single write, partition or not. That is latency you pay all day. A store that replicates asynchronously answers faster but can serve stale reads even when the network is perfectly healthy.

SystemPACELCReading
DynamoDB / Cassandra (default)PA / ELStays up during partitions; fast in normal operation; both bought with eventual consistency.
SpannerPC / ECRefuses rather than diverge during partitions; spends latency (TrueTime waits) on consistency always.
MongoDB (default majority)PC / ECLeader-based; minority side can't elect, so it blocks; waits for majority acks normally.
PostgreSQL single-primary + async replicaPC / ELOne primary so no divergence; async replica reads can be stale with no partition.
Classifications follow Abadi's PACELC write-up; real systems are tunable per-request, so treat these as the default posture, not a fixed identity.

Your feature needs single-digit-millisecond writes and can tolerate a reader occasionally seeing a value 50 ms old. Which posture fits?

You explicitly accepted staleness and demanded low latency — that is the EL choice, and taking availability during partitions too (PA) is consistent with it. A PC/EC store like Spanner would add coordination latency you said you can't afford.

4. How to say it in the room

Template sentence "This path is [read-heavy / write-heavy] and can tolerate [X ms] of staleness, so I'll pick an EL store and take PA during partitions — I'd rather serve a slightly stale timeline than 500 the user. For the [payments / inventory] path I flip to PC/EC and accept the write-latency and the partition-time unavailability, because a double-charge is unrecoverable."

Two things that move you from Senior to Staff here: (1) you split the system — different paths get different postures; (2) you name the cost of your choice unprompted, not just the benefit.

Read this next (primary source): Martin Kleppmann — "Please stop calling databases CP or AP" (2015). 15 minutes. It sharpens exactly why the definitions above are so narrow, and why a single label per database is a lie. Then skim Abadi's PACELC note.

Recall (do this from memory, no scrolling)

Which statement about CAP is correct?

CAP is silent absent a partition (that's what PACELC's "else" covers), partitions can't be designed away, and CAP-availability has no latency requirement — only "eventually a non-error response".
