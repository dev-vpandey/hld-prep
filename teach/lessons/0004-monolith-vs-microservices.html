Monolith → modular monolith → microservices

Lesson 0004 · System Design Fundamentals · Section 1 · ~7 min

Mission tie-in: at Staff level the interesting answer is almost never "microservices" reflexively. It's knowing when the split pays for itself and what it costs — the operational tax, the consistency problem, Conway's Law. Reflexive microservices is a downlevel tell.

2. The modular-monolith discipline

A modular monolith is one deployable, but internally split by business domain, modules talking only through public APIs.

"One module should never directly query another module's database tables — it must always go through its public API."

This is the cheap 80%: you get domain boundaries and team ownership without the network, without distributed transactions, without a tracing stack. And it's the clean extraction path if a module later needs to become a service.

3. What microservices actually cost

  • Network reliability — every in-process call becomes a fallible RPC needing timeouts, retries, circuit breakers.
  • Data consistency — no cross-service transaction; you're now in eventual-consistency / saga territory (Lesson 0001's trade-offs, per call).
  • Operational overhead — service discovery, API gateway, distributed tracing, per-service CI/CD, on-call for N services.
"Adopting microservices too early can cripple a startup with operational overhead before it even finds product-market fit."

4. The selection framework

Decide on Team size & structure (Conway's Law — your services will mirror your org chart) · business stage (early = iterate fast = monolith) · divergent scaling needs across features (favours the split) · operational maturity (no tracing/discovery expertise → the tax outweighs the benefit).

Default recommendation to give in an interview: start with a well-structured modular monolith, extract services only where scaling or deploy-cadence needs genuinely diverge.

A 12-person startup, pre-PMF, one product, uniform load. Interviewer asks how you'd structure the backend. Best answer?

Microservices impose an operational tax this team can't absorb pre-PMF and gains them nothing with uniform load. A boundary-less monolith rots. The modular monolith keeps iteration speed while preserving a clean extraction path.
Read this next (primary source): Martin Fowler — "MonolithFirst" and "Microservice Premium". ~15 min combined. The canonical case for not starting distributed.

Recall

Which cost is unique to microservices, not modular monoliths?

API-only communication and domain boundaries apply to modular monoliths too. The network — partial failure between services — is the tax you only pay once calls cross a process boundary.
